## A bug I found and fixed in my own draft

The brief's Step 7 header comment for `webapp.ttl` reads: *"Copy what your domain needs
into ontology/{{ONTOLOGY_FILE}}..."* — i.e. it puts a `{{TOKEN}}` inside
`ontology/examples/webapp.ttl`. That file is **not** in `init.py`'s `MANIFEST`
(Correction 3 says the manifest covers only `ontology/<ontology_file>` and
`specs/example/spec.ttl`), and `remaining_placeholders` sweeps the *entire* tree
(`.ttl` is in `TEXT_SUFFIXES`) regardless of MANIFEST membership. Following the brief
literally would have left an unsubstitutable `{{ONTOLOGY_FILE}}` in every generated
repository forever, permanently failing `init --check`.

I verified this empirically: with the token in place, `knowledge init --check` reported
`ontology/examples/webapp.ttl: {{TOKEN}}` as one of the "not substituted" placeholders —
confirming `remaining_placeholders` does sweep files outside the manifest. I rewrote the
header comment to name the actual default filename (`ontology.ttl`) in plain prose
instead of the token, and to say explicitly that this file carries no placeholder because
it isn't part of `init`'s substitution manifest. I also had to word that explanation
without literally typing `{{...}}` — my first attempt at the sentence used the literal
string `{{TOKEN}}` as an example and the placeholder regex matched *that*, which I caught
via the same `init --check` run and rewrote as "double-brace placeholder" instead.

## `concept_spec` naming a non-existent spec — verified, not assumed

`knowledge.toml` ships `concept_class = ""` and `concept_spec = "concepts"`. I read
`lint.locally_redeclared_concepts`:

```python
def locally_redeclared_concepts(paths: Paths, vocab: Vocabulary, ids) -> list[str] | None:
    checks = vocab.checks
    if not checks.concept_class or not checks.concept_spec:
        return None
    ...
```

The guard is `or`, so an empty `concept_class` alone is enough to return `None` — it
never reaches the point of resolving `concept_spec` against a spec directory that
doesn't exist, so `specs/concepts/` never having been created causes no error. I
confirmed this is not just a code-reading conclusion but the actual runtime behaviour:
the `validate --strict` transcript above shows `skipped (not configured): concept(s)
redeclared locally instead of referenced` — the check ran (via the CLI, against the real
shipped config and the real `specs/example`) and reported skipped, not an exception, not
a false pass.

## `validate --strict` checks that report skipped, and why that's correct

Three of the eight checks report `skipped (not configured)` against the shipped
`knowledge.toml`:

- **naming violation(s)** (`lint.naming_violations`) — `field_class` is empty, so there
  is no field class for the pattern/underscore checks to apply to. Returns `None`.
- **concept(s) redeclared locally instead of referenced** (`lint.locally_redeclared_concepts`)
  — `concept_class` is empty (see above). Returns `None`.
- **ungrounded literal(s) no prose states** (`lint.ungrounded_literals`) —
  `verbatim_string_properties` is `[]`. Returns `None`.

The other five checks are unconditional or gated only by `rule_class` (which the seed
does set), so they run and pass cleanly: dangling terms, broken links, invented
predicates/types, restated rule comments (the example `Rule`'s comment is a real reason,
not a restated label), and domain/range violations.

## Self-review

**Is the guide something a stranger could actually follow?** I wrote each `AUTHORING.md`
section around one worked SPARQL/Turtle snippet grounded in either the seed
(`ex:constrains`) or the worked example (`web:partOf`/`web:contains`/`web:route`), rather
than abstract advice. Each section states the RDFS mechanism that makes the rule true
(no built-in transitivity, two ranges read as an intersection, no `owl:FunctionalProperty`
without OWL) rather than just asserting "do it this way" — so a reader can verify the
reasoning against the ontology docs rather than take it on faith. The closing checklist
gives a direct term-to-config-key mapping, which is the thing someone editing the
ontology actually needs at the moment they add a term.

**Is the seed genuinely minimal rather than a trimmed-down monicords?** Yes — `Concept`,
`Rule`, `Actor` and three properties are the only terms, with no monicords-specific
concept (no `InterfaceElement`, `View`, `Field`, `route`, `viewport`, etc. — those all
live only in `ontology/examples/webapp.ttl`, the sanctioned worked example). The seed's
own comments explain *why* each design choice was made (symmetric-but-not-inferred,
no-range-for-cross-type) using the seed's own tiny vocabulary, not by reference to the
webapp example — so the seed stands on its own as something to read and delete from,
independent of the guide.
